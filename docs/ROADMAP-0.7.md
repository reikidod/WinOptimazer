# WinOptimizer 0.7 — дорожная карта до завершения

**Цель:** превратить текущий Performance Center в надёжный, понятный и безопасный центр наблюдения за производительностью Windows 10/11. Работа ведётся только в ветке `beta`. Стабильная ветка `main` не изменяется.

## Принципы готовности

- Корректность важнее количества датчиков: недоступное значение отображается как «н/д», а не как ноль.
- Сбор метрик не блокирует UI и не создаёт заметной фоновой нагрузки.
- Любая рекомендация содержит наблюдаемое основание, объяснение, ожидаемый эффект, риск и уверенность.
- Никаких автоматических завершений процессов, отключений служб, изменения реестра или планировщика.
- Системные изменения возможны только после отдельного подтверждения пользователя; Task Scheduler остаётся read-only.
- Данные остаются локальными. Для сохраняемой истории нужны ограничение объёма, срок хранения и очистка.
- Каждый этап заканчивается тестами, проверкой diff и успешным GitHub Actions.

## Этап 1. Надёжный сбор метрик — в работе

**Текущий прогресс:** подключены Windows `PhysicalDisk` и `GPU Engine` Performance Counters, а температуры CPU/GPU/NVMe считываются через необязательные WMI-провайдеры LibreHardwareMonitor/OpenHardwareMonitor. Метрики CPU/RAM, сети, GPU, физических дисков и температур приводятся к общему контракту с единицами, источником, временем и состоянием доступности. Первый замер помечается как прогрев, недоступные датчики — как «н/д». Проверка на реальном Windows-железе и smoke-тест WMI-провайдеров остаются обязательными.


- [x] CPU и RAM: текущие значения и базовая история в памяти сеанса.
- [x] Сетевая скорость: расчёт по дельтам счётчиков, обработка сброса/недоступности.
- [x] GPU: загрузка по Windows GPU Engine counters; группировка нескольких адаптеров, суммирование процессов по физическому движку, прогрев и изоляция недоступных счётчиков. Реальная поддержка зависит от драйвера и требует smoke-проверки на Windows.
- [x] Диски: сбор активности/скорости чтения-записи по штатным `PhysicalDisk` счётчикам раздельно по экземплярам; заполнение тома остаётся отдельной метрикой. Реальное поведение счётчиков требует smoke-проверки на Windows.
- [x] Температуры: читать датчики CPU/GPU/NVMe из необязательных WMI-провайдеров LibreHardwareMonitor/OpenHardwareMonitor; показывать источник и время обновления; ACPI Thermal Zone не выдаётся за температуру CPU. Требуется smoke-проверка с установленным провайдером и реальными датчиками.
- [x] Единый контракт метрики используется CPU/RAM, сетью, GPU, физическими дисками и температурными датчиками: значение, единица, источник, timestamp, состояние доступности и причина отсутствия.
- [x] Изолировать ошибки отдельных GPU/дисковых счётчиков и освобождать ресурсы при завершении приложения.
- [x] Единая политика интервалов: панель — 2 с, переобнаружение GPU/дисков — 15 с, температуры — 5 с, максимальный разрыв для дельт — 30 с.
- [ ] Тесты длительной работы и измерение фактической нагрузки всех источников.

**Критерии:** тесты на парсинг, нулевые/отрицательные/переполняющиеся счётчики, пропуски данных, несколько адаптеров и дисков; сбор метрик не блокирует интерфейс.

## Этап 4. Объяснимые рекомендации

- [ ] Никаких автоматических исправлений и навязчивых действий.

**Критерии:** детерминированные unit-тесты порогов, пограничных значений, неизвестных данных и подавления повторов.

## Что не входит в 0.7

- Синхронизация приложения с сайтом/учётной записью.
- Удалённое управление и отправка телеметрии на сервер.
- Автоматическая оптимизация или применение рекомендаций без подтверждения.
- Изменение задач Планировщика Windows (он остаётся read-only).
- Массовый рефакторинг или новые функции вне Performance Center.

## Рабочий протокол каждого продолжения

1. Проверить актуальный HEAD `beta`, открытые PR и последние Actions.
2. Сверить код и тесты с текущим этапом; не предполагать, что прошлое состояние осталось неизменным.
3. Выполнить небольшой связный блок работ, добавить тесты и обновить CHANGELOG.
4. Создать коммит и продвинуть только `beta` с проверкой ожидаемого SHA.
5. Дождаться CI; при ошибке изучить лог, исправить минимально и повторить.
6. Переходить дальше только после зелёных проверок. Финал — после этапа 7 и подтверждённого тестового релиза.
